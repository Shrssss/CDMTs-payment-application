### 3. `createPayment` のトークン保護

`POST /api/payments/create/{orderId}/{sourceId}` は、呼び出し元が対象`orderId`の正当な本人であることを検証していません。`orderId`は連番でありAPIを叩けば誰でも生成できてしまうため、他人の注文IDを指定して決済結果を紐付けることが可能です。下記「6. 注文照会用トークンAPI」のトークンを用いた検証を組み込んでください。

### 4. `OrderResponse` への `paymentStatus` 再追加

現行の`OrderResponse`(`model/dto/OrderResponse.java`)には`paymentStatus`が含まれていません。`cooking.js`側には「`paymentStatus`が`true`の注文のみ表示する」ロジックが存在するため、このフィールドが無いと該当ロジックが機能しません(旧設計ではエンティティを直接返していたため自動的に含まれていました)。業務ルールとして必要であれば追加をお願いします。

### 5. ドリンク割り振りのサーバー側実装

**フロント側は対応済みです(2026-08-30)。** `POST /api/orders/set`のリクエストボディに`drinkCounts`(`{drinkId: count}`)を追加送信するようになりました。現行バックエンドはこのフィールドを無視するだけなので、既存の動作は壊れません。バックエンド側の対応(下記)が完了次第、双方が噛み合います。

現行の商品ID設計(内訳ID 31-34/41-44/51-54を、セットID+ドリンクオフセットの演算で合成し、実在の商品として送信する方式)には以下の問題があります。

- 商品登録API(`POST /api/items`)は`itemId`を常に`null`で渡す実装(`ItemCreateRequest.toEntity()`)であり、クライアント側が特定のIDを狙って商品マスタへ登録する手段がありません。内訳ID(31-34等)を意図した商品として登録する方法が現状存在しません。
- `OrderService.createOrder()`は商品IDの実在チェックを行わないため、実在しない内訳IDを送信すると、注文作成の失敗、または決済計算時(`PaymentService.createPayment()`内の`itemMap.get(orderItem.getItemId()).getPrice()`)でのNullPointerExceptionを引き起こす可能性があります。

**提案する変更**:
- 商品ID(`itemId`)とドリンク種別ID(`drinkId`)を合成せず、別々のフィールドとして扱う設計に変更してください。
- `ORDER_ITEM_TABLE`に`DRINK_ID`列(NULL許容)を追加してください。価格計算は常に`ITEMID`(親カテゴリ: 10/20/30/40/50の商品マスタ価格)のみを参照し、`DRINK_ID`は価格に影響しない付随情報(調理側が何の飲み物を用意すればよいかの表示用)として扱ってください。
- どのカテゴリ(セット/大盛りセット/単品ドリンク)にどのドリンクを割り振るかの計算ロジック(先着順の詰め込み処理。詳細は下記「データ形状」参照)は、フロントエンドの`cartOrganizer.js`にあった実装を移植してください。
- これにより、仕様書8.2章に記載の「内訳IDを実商品として送信する」という前提は撤回してください。

**データ形状(フロント→バック、注文作成時)**:
```json
{
  "orderDate": "...",
  "reservedTime": "...",
  "servingStatus": 0,
  "paymentStatus": false,
  "items": [
    { "itemId": 10, "quantity": 1 },
    { "itemId": 40, "quantity": 2 }
  ],
  "drinkCounts": { "91": 1, "92": 1 }
}
```
`items`はカテゴリ別の生の数量、`drinkCounts`はドリンク種別ごとの合計数(どのカテゴリに属するかは紐付けない生データ)です。割り振り計算はサーバー側で行ってください。

**割り振りアルゴリズム(参考、`cartOrganizer.js`から移植)**:
ドリンク種別を固定順(コーラ→オレンジ→サイダー→烏龍茶)に処理し、各ドリンクについて「まずセット(40)の未割り当て分から埋め、余ったら大盛りセット(50)、それでも余ったら単品ドリンク(30)」という優先順位で先着順に割り当てる、単純な数合わせロジックです(特定のセット個体に特定の好みを紐付けるものではありません)。

**データ形状(バック→フロント、注文取得・照会時)**:
`OrderResponse.orderedItems`の各行に`itemId`/`itemName`/`quantity`に加えて`drinkId`/`drinkName`(ドリンクを伴わない商品は`null`)を持たせてください。

```json
{
  "orderId": 12,
  "orderDate": "2026-08-29T12:00:00",
  "reservedTime": "2026-08-29T12:30:00",
  "servingStatus": 0,
  "orderedItems": [
    { "itemId": 10, "itemName": "角煮 単品", "quantity": 1, "drinkId": null, "drinkName": null },
    { "itemId": 40, "itemName": "角煮ドリンクセット", "quantity": 1, "drinkId": 91, "drinkName": "コーラ" },
    { "itemId": 40, "itemName": "角煮ドリンクセット", "quantity": 1, "drinkId": 92, "drinkName": "なっちゃんオレンジ" }
  ]
}
```
同じ`itemId`でも`drinkId`が異なれば別の明細行になります(`quantity`は「同じitemId+drinkIdの組み合わせが何個か」)。

### 6. 注文照会用トークンAPIの新設

現在、注文の照会・状態管理は連番の`orderId`をそのまま使っていますが、これは推測可能なため、他人の注文を覗き見・操作できてしまいます(項目2・3参照)。

- 注文作成時にサーバー側でランダムな推測不可能なトークン(例: UUID)を生成し、レスポンスに含めて返してください。
- トークンから注文内容を取得する新規エンドポイント(例: `GET /api/orders/get/byToken/{token}`)を追加してください。無効なトークンにはエラーを返してください。
- 同一客が複数回注文した場合、新しい注文ごとに新しいトークンを発行してください。**古いトークンは無効化・破棄しないでください**(過去の注文も引き続き参照できる状態を維持)。
- フロントエンドはこのトークンのみをCookieに保存し、`orderId`そのものは保持しません。

### 7. カート確認用の価格計算API新設

**優先度が下がりました。** フロント側で再検討した結果、価格はカテゴリ(`itemId`)単位でのみ決まりドリンクの種類には影響しないため、カート確認画面(決済前)の合計金額表示は、既に取得済みの商品マスタ価格(`GET /api/items/get/allItems`)だけで正しく計算できることを確認しました。このAPIは新設不要という判断です。ただし、**注文作成API自体がクライアント指定の金額を信用せず、サーバー側で計算し直す**という設計原則(下記)は、`OrderCreateRequest`が既に体現している通り引き続き重要です。

(参考: 元の提案) 注文作成前に、カテゴリ別数量+ドリンク種別ごとの合計数から金額を計算して返す、**副作用なし(DB書き込みなし)の表示専用エンドポイント**を新設してください。

**重要な設計原則**:
- このAPIが返す「整形済み注文・金額」を、そのままクライアントが注文作成APIへ再送信する設計にしないでください。往復の間にクライアント側で改ざんされうるためです。
- 注文作成APIは、この価格計算APIの結果を信用せず、**同じ生の入力(カテゴリ別数量+ドリンク種別ごとの合計数)を独立して受け取り、商品マスタの価格から毎回サーバー側で計算し直して**ください。(現行`OrderCreateRequest`が`amount`フィールドを持たず、クライアント指定の金額をそもそも受け取らない設計になっているのは、この原則に沿っており正しい実装です。新設APIでもこの原則を維持してください。)
- 「価格計算API(表示用)」と「注文作成API(実際に使う金額を決定)」を別々に実装すると、片方だけ修正されて金額がズレる不具合が起きえます。**両APIは同じ価格計算ロジック(同一の関数/メソッド)を共有する実装にしてください。**
- Square/PayPayへ渡す決済金額は、注文作成APIのレスポンスで返された金額をそのまま使う想定です(フロント側では再計算しません)。表示・注文作成・決済の3箇所で金額の発生源を1つに統一してください。

### 9. 注文作成時に予約時刻(`reservedTime`)を営業時間内かサーバー側でも検証してほしい

現状、最終受付時刻(17:10)の制御はフロントエンド(`School-Festival-2`)側の画面表示・ボタン無効化でのみ行っています。`POST /api/orders/set`は`reservedTime`が営業時間内かどうかを一切検証していないため、フロントを経由せず直接APIを叩けば、17:10以降や過去の日時を指定した注文も普通に作成できてしまいます。

項目7で述べた「クライアントを信用せず、サーバー側で再検証する」という原則と同じ理由で、営業時間(開始時刻・最終受付時刻)についても`OrderService.createOrder()`側で検証し、範囲外の`reservedTime`はエラーで拒否するようにしてください。営業時間の値自体は運用上変わりうるので、設定値として一箇所にまとめておくことをおすすめします(現状フロント側は`RESERVATION_CONFIG`という定数にまとめています)。
