- カード／PayPayの外部POST前に、注文番号・SID・方式・カート・予約日時・作成日時を `sessionStorage` の `cm_pending_payment_v1` へ保存。カードトークンとメールは保存せず、保存不能時は外部POSTを行いません。
- 起動時に `paysys_return`・`result`・`SID`・`ERROR` と保留注文を照合。PayPayの取引パラメータなしRTと再読み込みでも同じタブの注文を復元します。方式／SID不一致・保存欠落では取引を推測しません。
- 復帰先の成否によらず保存済み注文の状態APIを呼び、`WAITING`／`PAID` を受け取ります。HTTPエラー・応答不整合は未確認として保持します。

### M12：確認中表示・再取得・完了保存

- M11コミット：`de668cf`。
- `WAITING`・通信失敗時は確認中を表示し、新しい決済の再試行ボタンは表示しません。手動の状態再取得を追加し、照会中はボタンを無効にします。
- 保存欠落・SID不一致は注文を確認できない画面と係員への案内を表示し、別注文を推測して照会しません。
- 状態APIが `PAID` の場合だけ、実注文番号・元のカート・予約日時を既存 `cm_order_v1` 形式で保存し、番号札に引き継ぎます。保存後に保留データと復帰クエリを除去します。完了保存不能時は支払済み表示と保留注文を維持し、再読み込みで再照会できます。

### 3-4. 文字コードと送信方法

自アプリのReact ↔ JavaのAPIはUTF-8のJSONを使って構いません。**Paysysとの境界は、仕様のパラメータ付きPOST／GET、Shift-JISへ変換します。** カードの3DSとPayPayはブラウザの画面遷移であり、外部URLへJSONをfetchする処理ではありません。

- 実装方針はPOSTとし、サーバー通信では `application/x-www-form-urlencoded` の各値をShift-JISのバイト列からURLエンコードする。UTF-8でエンコードしてからヘッダーだけShift-JISに変えない。
- ブラウザの外部遷移は通常のフォーム送信を使う。最初は上表のようにASCII値だけで構成し、UTF-8のReact画面から送っても符号化の差が出ない範囲に限定する。
- 日本語を外部フォームへ入れる場合は、UTF-8画面に `accept-charset` を付けるだけでShift-JISになると決めつけない。サーバーでShift-JISとして配信する中継HTML等を設計し、実送信バイトを検証する。
- 通知・照会の受信処理でもShift-JISを考慮する。SpringのUTF-8既定設定のまま日本語を正しく読めると考えず、Paysys用経路でフォーム／クエリの復号方法を決める。
- カード確定照会はJSON応答ではなく `text/plain;charset=Shift_JIS`。改行はCRLF。`C-CHECK:OK` など本文を解析し、HTTP 200だけで成功としない。

| API案 | 用途 | 主な入力・出力 |

お客様用の決済開始・状態取得・注文照会では、注文番号だけでアクセスを許可しません。注文作成時に発行した推測困難なトークンを、`Authorization: Bearer ...` ヘッダーで送る設計案に統一します（Codex作成）。新規注文ごとに別トークンを発行し、過去の注文用トークンを一括で上書きしないでください。

Codex案では注文ごとに32バイト乱数のBearerを発行し、有効期間7日、localStorageに複数注文として保存します。通常はハッシュをDBに保存し、注文作成の同一応答再送のためだけに暗号化応答を24時間保管します。XSS対策・再送キーの保護を含め、詳細はAPI仕様2・4章を参照してください。顧客Cookie認証は採用しません。

注文作成レスポンスの案：

```json
{
  "orderId": "123",
  "orderToken": "サーバーが生成した推測困難な値",
  "amount": 900,
  "currency": "JPY",
  "paymentState": "UNPAID"
}
```

現状は注文番号だけが返るため、バックエンドの返り値を変更したらフロントの型と読み取り処理も同時に直します。

決済準備APIのレスポンスには、例えば `nextAction.type=FORM_POST`、`action`、`fields` を持たせます。これは自アプリが組み立てるJSONであり、PaysysがJSONや決済URL発行APIを提供するという意味ではありません。準備APIでは外部決済を実行せず、フロントがフォームPOSTして決済画面へ遷移します。外部POST先・IPコード・金額・STORE・戻りURLはサーバーで固定／決定し、ブラウザから任意の値を指定させません。`PASS` はレスポンスに含めません。

ブラウザへ渡したフォームは利用者が変更できるため、決済準備時の検証だけでは十分ではありません。完了判定時にも、サーバー保存済みの契約・SID・方式・金額・売上確定状態との一致を検証します。不一致は調理対象にせず、担当者による照合・必要なアプリ外の取消／返金対応へ回します。

決済状態は、例えば次のように区別します。これらは内部名称です。カードは確定照会、PayPayは検証済み完了通知を根拠にします。信頼できる外部終結を確認できない場合はUNKNOWNを維持します。戻りURLや通知未着だけから失敗・期限切れを断定しません。

| 状態案 | 意味 | お客様への表示 |
|---|---|---|
| `UNPAID` | 決済未開始 | 支払いへ進む |
| `PROCESSING` | 本人認証・支払い操作・結果待ち | 支払い手続き中 |
| `UNKNOWN` | 通信切断などで成否未確認 | 結果を確認中。追加の支払いを促さない |
| `PAID` | サーバーが売上確定を確認した | 支払い完了 |
| `FAILED` | 失敗を確認した | 再試行できるか案内 |
| `CANCELED` / `EXPIRED` | 取消・期限切れを確認した | 取消・期限切れ |

想定外の与信はUNKNOWN＋要調査として扱い、自動売上確定しません。返金状態・操作APIは設けず、アプリ外返品は運用台帳と別担当の提供停止へ連携します。提供条件はPAIDかつ要調査なしです。時間設定・再試行条件は接続仕様5章とAPI仕様8章に統一します。

**完了条件：** 自アプリAPIのJSON例、外部フォーム項目、通知の受信・応答形式、認証方法、状態遷移、再試行ルールが文書になっている。

「必須」は、現行コードのままではカード・PayPayの正常な決済開始、注文への結果反映、外部画面からの復帰を実装できない差分です。
「必須でないが重要」は、正常な1注文・1決済は実装できるが、認証・改ざん・重複・障害・本番運用を扱うための差分です。
「任意」は、構成の整理や表示・実装方式の選択です。Paysysの要求項目やSDK依存は外部接続条件なので必須ですが、自アプリのセキュリティ強化は必須に含めません。

### 5-3. 必須M01〜M03：現行の注文・金額・DBを使う

**現行の仕組み（2026-10-11）：** `Api.createOrder`は`POST /api/orders/set`へ注文を送り、`OrderController.createOrder`は素の注文番号（Long）を返します。`OrderService`は注文と明細を保存します。共通フック`useMockPaymentFlow`の非モック分岐は注文APIを呼び、注文番号を保持した未実装エラーを表示します。Paysys準備処理への接続と実通信の検証は未確認です。バックエンドの`PaymentService`は商品マスタの価格×数量による計算をSquare処理とPaysys準備処理で共用します。

1. **M01：注文作成を呼ぶ。** 支払い開始時に`buildOrderItems(cart)`で明細を作り、予約時刻を既存のLocalDateTime形式へ変換して`Api.createOrder`を呼びます。既存DTOが必須にしている`orderDate`・`reservedTime`・`servingStatus: 0`・`paymentStatus: false`を送ります。返った注文番号を次の決済処理へ渡します。既存`paymentSession.ts`は参考にできますが、呼ばれていないので、採用するならフックから実際に呼ぶ必要があります。

2. **M02：既存金額計算を再利用する（2026-10-08、サービス部分の作業終了）。** `PaymentService.calculateAmount`で商品マスタの単価×数量を合計し、`validateAmount`で検証します。数千円程度の利用を想定し、複雑化を避けるユーザ決定により、カード・PayPayともアプリ上限は`9_999_999L`円、許可範囲は1〜9,999,999円とします。外部仕様はカード7桁・PayPay8桁のままであり、PayPayにはより厳しいアプリ制約を適用します。方式別の上限分岐は作りません。

   現在の`preparePayment(Long orderId)`は注文の存在確認、明細・商品取得、計算・検証、SID保存を行い、`orderId`・`sid`・`amount`・`action`・`fields`を返します。`fields.K1`は合計の整数円文字列です。正の注文番号から`O`＋36進数表記のSIDを生成します（M03）。`action`は設定値です（M04）。準備メソッドはSquare呼出し・決済状態更新・Square用キーによる拒否を行いません。旧Squareの`createPayment`は残し、計算と検証を共用しています。新しい価格計算サービス・注文時単価保存は導入しません。

   2026-10-11のMockito単体テストは正常合計1,100円、上限超過10,000,000円、SID保存失敗の3件が成功。詳細は[試験記録](paysys_docs/payment-test-results.md)を参照。ユーザ指定により、サービス実装・単体検証をM02終了範囲とします。SID保存・接続設定はM03・M04で実装済み。準備APIの公開・方式別フォーム項目・フォーム接続は後続作業です。M02終了は工程3・4全体や外部決済接続の完了を意味しません。

3. **M03：SIDと注文を対応させる（作業完了）。** `O`＋正の注文番号の36進数表記をSIDにし、既存`Order.paymentId`／`ORDER_TABLE.PAYMENTID`へ保存します。正のLong最大値でも14文字で、半角英数字16文字以内です。`PaymentMapper.updateSidByOrderId`・`selectOrderBySid`と対応XMLを実装済み。開始情報を返す前に保存し、更新件数が1でなければ例外にします。実DBの列はユーザ確認で`PAYMENTID varchar(255) DEFAULT NULL`、列長変更のDDLは不要です。DB結合テスト2件の成功記録があります。全制約・既存データ・競合の検証完了を意味しません。

SID対応の機能は必須ですが、新規テーブルは必須ではありません。既存列の実際の型・長さ・制約を実DBで確認し、16文字以内のSIDを保存できるならDDLを追加しません。保存できない場合だけ該当列を調整し、`B/docs/db/001_paysys_payment.sql`へ記録します。注文番号をそのままSIDにするなら16文字制限を確認し、JavaのLongを無条件に10進文字列化しないでください。注文番号からSIDを一意に生成・逆変換する方式でも対応付けは実現でき、逆引きMapperの追加自体は必須ではありません。

`IDEMPOTENCY_KEY`は既存のSquare処理が使う項目です。Squareのキーがあることだけを理由にPaysys開始を拒否する旧分岐は、置換後の経路に適用しないよう調整します。新しい再送キーの設計や注文単位のロックはI05・I06で扱います。

**そのまま使うもの：** 注文作成の入力形式と注文番号だけの応答、注文・明細テーブル、予約ルール、商品ID、ドリンクの現行表現、提供状態。`drinkCounts`は現行バックエンドDTOに項目がなく、保存・割当も未実装です。この改善はI03で扱い、Paysysの課金接続とは区別します。

**工程3の完了条件：** モックを使わず既存APIで注文を作成でき、注文番号・現行計算による合計・SIDを決済処理へ渡せる。新しい注文Bearerや注文作成DTO、決済試行テーブルの実装を待たず工程4へ進める。

## 6. 工程4：必須のPaysys準備・通知・状態取得を接続する

### 6-1. 必須M04：使う接続設定だけを用意する

**2026-10-11、アプリ側設定の作業完了。** `application.yaml`と`PaymentService`で外部POST先・カード／PayPayのIPコード・公開origin・4種類の戻り先を読み込みます。公開originは`https://mobile-order.codemates.org`。戻り先はルート`/`に`paysys_return`と`result`のクエリを付け、絶対URLを組み立てます。詳細は[API契約0-4](paysys_docs/payment-api-contract.md#0-4-復帰用保存と既存表示)。ユーザによる起動確認成功、戻り先4件の直接実行検証成功（64〜70 ASCIIバイト）。通知は両方式POSTで、受信パスは`/api/payments/paysys/card/notify`・`/api/payments/paysys/paypay/notify`に決定済み。提供元への登録確認、フォームへの設定反映、通知受信、復帰処理は後続作業です。

開始処理が使うカード／PayPayの`IP`コード、ブラウザPOST先、方式別の戻り先・通知先を読み込めるようにします。Springはフロントの`.env.local`を自動で読まないため、バックエンドでフォームを作る場合はサーバーが参照できる設定へIPコード等を渡す変更が必要です。

| 設定・外部項目 | 必要な値・用途 |
|---|---|
| カード／PayPayのIPコード | 契約で指定された値。外部項目`IP`は契約コードであり、HTTPのIPアドレスやBearerではない |
| 外部POST先 | `https://www.paydesign.jp/settle/settle3/bp3.dll`。カード3DSとPayPayで共用 |
| トークンSDK | `https://www.paydesign.jp/settle/token/metapsToken-min.js` |
| 戻り先 | カード成功・失敗、PayPay成功・中止を識別でき、アプリが表示される公開URL。`OKURL`・`RT`は各ASCII100バイト以内。登録済みURLを使う場合は要求項目での上書きは不要 |
| 通知先 | カード／PayPayの通知受信URLと提供元に登録した送信方法。実接続では外部から到達でき、通知不要登録になっていない必要がある |

この開始・通知の最小フローは`PASS`を使用しません。IPパスワードを新たな必須設定として要求しません。専用`PaysysProperties.java`の新設はO01、Vite側のパスワード削除・サーバー秘密設定の整理はI10です。既存`application.yaml`を使うか、既存サービスから設定を読むかは実装の選択です。

### 6-2. 必須M02・M07：準備APIは外部課金を実行しない

`PaymentController`・`PaymentService`を変更し、注文番号からSID・現行計算金額・外部送信項目を準備してフロントへ返します。最小案は`POST /api/payments/card`と`POST /api/payments/paypay`を使います。正確なパスやDTOのクラス分割は外部仕様ではありませんが、既存の`sourceId`付きSquare APIのままではMAIL/TELやPayPayの要求を扱えないため、Paysys用の入出力処理は必要です。

注文作成の応答は注文番号のまま維持します。決済準備の応答にだけ`orderId`・`sid`・`amount`・`action`・`fields`を持たせます。詳細は[API仕様の最小契約](paysys_docs/payment-api-contract.md#0-最小実装のapi契約2026-10-04)を参照してください。Bearer、attemptId、Idempotency-Key、照合予約APIはこの段階の前提にしません。

準備APIの正常終了は「送信する情報ができた」という意味です。Squareの`create`と違い、この時点では支払いは完了していません。DBの`paymentStatus`をtrueにせず、フロントが通常のフォームPOSTを行って初めてPaysysの決済画面へ進みます。Paysysが決済URLを発行するAPIや、自アプリへのJSON課金応答を提供するとは扱いません。

### 6-3. 必須M09・M10：通知を受け、既存の決済状態へ反映する

`PaymentController`へのメソッド追加、または通知用Controllerにより、カード／PayPayの登録済みPOSTまたはGETパラメータを受けます。現行Controllerには通知受信処理がないため追加が必要です。JSONの`@RequestBody`だけではPaysysの通知を読めません。

| 通知項目 | 最小フローでの扱い |
|---|---|
| `SID` | 工程3の対応付けで注文を特定する |
| `KINGAKU` | 通知された支払い金額。カード7桁以内／PayPay8桁以内。最小状態取得の金額表示にも使える |
| `CVS` | PayPayは`paypay`、カードはブランド名等。開始要求の`STORE=42/51`とは別項目 |
| `SEQ` | 同じ通知の再送でも同じ番号。受け取れるようにする。監査保存・一意制約による重複管理はI07 |
| `IP`・`DATE`・`TIME`・`FUKA`等 | 登録・外部仕様に合わせて受け付ける。全項目のDB保存や通知専用テーブルは最小実装に含めない |

正常系では、SIDから対象注文を取り、既存`PaymentMapper`でその注文の`PAYMENT_STATUS=true`を保存してからHTTP 200、`Content-Type: text/plain`、本文1行目に半角`0`を返します。例えば`0\r\n`です。JSONや引用符付きの`"0"`ではありません。対象注文が存在しない場合や更新失敗時は正常処理完了の`0`を返さず、後半の再送・復旧処理へつなぎます。単純に同じ注文へtrueを設定する更新は、新しい注文や課金を発生させません。

**カードの最小フローの前提：** 自アプリが送る`KAKUTEI=1`の要求が変更されず、正常に完了した通知を処理する場合です。カード通知にはKAKUTEIがなく、与信のみの要求でも届くため、通知単独で任意の取引の売上確定を証明できるとは記載しません。改変・想定外の与信に対する確定照会、通知真正性、契約・金額照合はI07・I08へ分けます。旧版の「通知後に必ず確定照会してからPAID」は、重要項目を実装した後の最終方針です。

復帰した画面が結果を取得するため、`GET /api/payments/{orderId}/status`等の処理を追加します。現行`OrderResponse`は`paymentStatus`を返さないため、現在の注文照会だけでは支払いの完了を取得できません。既存`PaymentMapper.selectPaymentStatusByOrderId`を利用し、最小では`WAITING`／`PAID`を返します。falseは「未払いまたは結果待ち」であり、失敗・取消・期限切れの確定を意味しません。内部7状態のDB追加はO04です。

**工程4の完了条件：** 開始情報を準備でき、正常な方式別通知で該当注文を更新して`0`を返せる。ブラウザから注文の決済状態を取得できる。Bearer認証・監査テーブル・照合ジョブを完了条件に含めない。

## 7. 工程5：カードの必須入力・トークン・フォーム送信を実装する

### 7-1. 必須M05：PaysysのSDKでカードトークンを取得する

現行`PaymentPage.tsx`は支払いボタンだけで、`index.html`にもPaysys SDKの読込みがありません。`useCardPaymentFlow`は共通モックを呼ぶだけです。このままでは外部必須項目`TOKEN`を作れません。

1. `F/index.html`またはローダーでjQueryを読み、その後`metapsToken-min.js`を読み込みます。jQuery依存はカード仕様p.7に記載されています。独自ローダーの新設は不要です。
2. 採用済みのポップアップ方式として、ボタン操作から`metapspayment.createTokenWin(callback)`を呼びます。3DS用にカード名義人を必須とするSDK設定を適用します。セキュリティコードの扱いはSDK・契約の入力条件に合わせます。
3. コールバックの`status === 201`、エラーなし、`response.id`を確認し、その16文字トークンをカード準備処理へ渡します。SDK未読込・取得失敗時はフォームを送らず、入力をやり直せる表示にします。
4. 取得から15分、有効使用1回の外部仕様を守ります。成功通知待ちの再照合と、新トークンを使う再決済は区別します。新しい再試行ルールや保存保護はI05・I08・I10で扱います。

TypeScriptからSDKを呼ぶために必要な宣言は既存型ファイルまたは局所的な宣言へ追加します。新規`paysysCardService.ts`や`types/paysys.d.ts`への分割そのものはO01です。

### 7-2. 必須M06：3DS用連絡先を1種類用意する

カード仕様p.11は、3DS時にMAILまたはTELの少なくとも一方を要求しています。現行画面はどちらも入力しないため、入力欄とフックへの引数追加が必要です。最小案ではメール欄1つを追加し、MAILに渡します。電話欄も併設することは必須ではありません。

MAILは100バイト以内の制限付きASCIIで、記号は`- _ . @`のみです。TELを代わりに採用するなら数字9・10・11桁で送ります。外部仕様に適合する値を送ることは必須ですが、フロント・バックエンド両方での重複検証や一般注文DTO全体の厳格化はI03です。住所・国番号等の任意3DS項目はO08として扱います。

### 7-3. 必須M07・M08：モックを実通信へ置き換える

`useCardPaymentFlow.ts`で、トークン取得→既存注文API→カード準備API→通常のフォームPOSTを接続します。モックを無効にしたときに現在の「未実装」分岐へ入る状態を解消します。`useMockPaymentFlow`を全面改修する必要はなく、モック時は既存処理、実通信時はカード固有処理とします。

| フォーム項目 | カードで送る値 |
|---|---|
| `IP`・`SID` | 契約のIPコードと、注文に対応付けたSID |
| `STORE`・`K1` | `51`、既存計算による整数円の合計 |
| `TOKEN` | SDKの`response.id` |
| `KAKUTEI` | 採用済みの即時売上確定として`1`を明示 |
| `MAIL`または`TEL` | 前節で取得した連絡先 |
| `OKURL`・`RT` | 工程4で設定した戻り先。登録済み戻り先を使う構成では要求から省略可能 |

送信先は`bp3.dll`です。`fetch`で課金完了JSONを取得する処理や、先に標準決済`ubp3.dll`を呼ぶ処理は作りません。ブラウザから外部ページへの遷移が3DS方式に必要です。

外部仕様はShift-JISです。最小フォームでは必須項目をASCII範囲に限定し、N1・FUKA等の日本語を送らなければ、ASCII部分はUTF-8とShift-JISで同じバイトになります。日本語項目を送る場合だけ、仕様に沿うバイト列・URLエンコードを実装します。`accept-charset`の指定だけで現行ブラウザがShift-JIS送信すると仮定せず、実際の送信データを確認します。

**工程5の完了条件：** モック無効で、カードトークン・必要連絡先・注文・開始フォームが作成され、提供元の試験条件下で3DS画面へ進める。SDKの文言変更や独自カード入力画面を作る必要はない。

## 8. 工程6：PayPay送信と両方式の復帰を実装する

### 8-1. 必須M07・M08：PayPay固有の要求を接続する

`usePayPayPaymentFlow.ts`の実通信分岐で、既存注文API→PayPay準備API→フォームPOSTを行います。カードのSDK・トークン取得は使いません。`PaymentPayPayPage.tsx`の既存ボタンをそのまま起点にできます。

`bp3.dll`へ`IP`・`SID`・`STORE=42`・`K1`と、必要に応じて登録済み戻り先を上書きする`OKURL`・`RT`を送ります。`TOKEN`・`KAKUTEI`は送らず、`PASS`も今回の開始方式には不要です。`N1`は推奨項目であり必須ではありません。日本語の商品名を付けない最小案では文字コード変換処理を増やしません。

### 8-2. 必須M11：外部遷移前に進行中注文を保存する

現行`App.tsx`は起動時にReactの初期状態を作り、戻りURLの解釈を行いません。外部サイトへ遷移するとメモリ上の注文・カート・予約が失われるため、復帰処理を追加する必要があります。

1. 外部POST前に、進行中の注文番号・SID・方式・カート・予約時刻を保存します。最小案はタブ内の1件を`sessionStorage`に保持します。カードトークンや連絡先を復帰用データへ入れる必要はありません。
2. 完了済み注文に使う既存`cm_order_v1`とは別の保留データにします。既存`viewSavedOrder`はスナップショットがあれば無条件に`ok: true`として番号札を出すため、そこへ支払い前データを保存すると既存の完了扱いに混ざります。
3. 戻り先は既存アプリのルート`/`に方式・復帰種別のクエリを付ける案とし、`App.tsx`等の起動時処理で復帰を識別します。ルートは現在の`WebConfig`で`index.html`へ転送するため、新しいSPAルートやViewController追加は前提にしません。配信先でもこのURLからアプリが表示されることを確認します。

## 9. 工程7：最小限の結果表示を既存画面へ反映する

### 9-1. 必須M12：通知待ちを失敗表示にしない

`PaymentResultPage.tsx`は現状`outcome.ok`のtrue／falseだけで成功と失敗を表示します。Paysysの通知は外部遷移と別の通信なので、復帰時点では未着の場合があります。falseをすべて「決済に失敗しました」にすると、正常な通知待ちも失敗表示になるため、結果待ちの表示を追加します。

最小案ではフロントの`PaymentOutcome`に待機状態を表すフィールドを追加し、状態APIが`WAITING`なら「決済結果を確認中」、`PAID`なら既存の完了表示と番号札への導線を使います。WAITINGの間は新たな決済を開始する再試行ボタンを出さず、状態再取得の操作を用意します。自動ポーリングの間隔・上限やUNKNOWN・要調査フラグはI09で扱い、最小では手動更新でも結果を取得できます。

SDK取得失敗・自アプリへの要求失敗など、外部へ送る前の失敗は既存のエラー表示を使えます。カードの外部ERRORは「手続きが完了していない」案内の材料にし、PayPayにも同じERROR_CODEが戻ると仮定しません。全エラーコードの細分類、取消・期限切れ専用画面はO04・O09です。

### 9-2. 必須M11・M12：既存スナップショットと番号札へ引き継ぐ

状態APIで完了を取得したら、保存済みカート・予約・実際の注文番号から既存形式の完了スナップショットを作り、既存の`paymentResult`／`numberTag`へ渡します。保留データは完了後に片付けます。`Order.tsx`・`NumberTagPage.tsx`に同じデータを渡せるなら、その表示構造は変更しません。

既存の完了スナップショット全件を再照会する変更、保護付き`fetchOrder`の新設、商品名・単価・ドリンクのサーバー明細による表示はI01・I04・I14です。未払い注文の提供拒否、スタッフ認証、従業員画面の旧API修正はI11・I12として別担当との後続連携に分けます。

**工程7の完了条件：** 正常な通知後に実際の注文番号で完了表示・番号札を出せる。未着なら確認中を表示して状態を再取得できる。従業員画面の改修・認証・全保存注文の再検証を完了条件に含めない。

`drinkCounts` の割り振りは `F/docs/backend-requirements.md` の項目5を参照し、必要に応じて `F/src/features/order/cartOrganizer.ts` を参考にします。存在しない合成商品IDを決済計算に使わず、商品IDとドリンクIDを別項目にします。

### 12-2. DB変更を記録する

追加変更の保存先案：`B/docs/db/002_order_spec_improvements.sql`。工程3でDDLが不要なら`001_paysys_payment.sql`の作成・適用は不要です。既に適用した差分がある場合だけそれを前提にし、適用済みSQLを書き換えて再適用しないでください。

これは**手動適用用SQLの保存先案**です。この場所に置くだけでは実行されません。実DBの定義を確認し、開発DBで適用・復元を確認してから本番適用手順を作ります。

| 最終的な変更対象案（工程3で実装済みの項目は再作成しない） | 保存する情報 |
|---|---|
| `ORDER_TABLE` | 確定金額、通貨、内部決済状態、照会用トークンのハッシュ、注文作成の重複防止キー |
| `ORDER_ITEM_TABLE` | 注文時単価、ドリンクID |
| 新規 `PAYMENT_ATTEMPT_TABLE` | 注文ID、決済手段、試行ID、IPコードに対応する契約設定、SID（半角英数字16文字以内）、金額、カードのKAKUTEI、状態、作成・更新日時 |
| 新規通知記録テーブル | 決済方式・契約、SEQ（10桁以内）、SID、KINGAKU、受信日時、検証・処理結果 |

一意制約や注文行のロック等を用いて、カード／PayPayを切り替えた同時要求でも有効な試行が重複しないようにします。今回の資料の取引照合キーは `SID` です。別の「Paysys取引ID」が必ず返る設計にはしません。

通知の再送は同じ `SEQ` です（カード p.23／PayPay p.9）。一意キーは契約・方式・SEQを含める案とし、連番の採番範囲は提供元に確認します。重複時は保存済みSID・金額等との一致も検証し、内容が異なる場合は無条件に成功応答しません。

既存データの移行方針も書きます。過去のSquare取引を誤ってPaysys取引として扱わないでください。会計上必要な履歴は保持し、Squareを呼び出す実行経路を撤去します。
