## 1. 決済の仕組みを刷新(Square廃止 → 自社決済「PaySys」へ移行)

### ひとことで言うと

これまでクレジットカード決済には外部サービス「Square」を使う予定で準備が進んでいましたが、**Squareの利用をやめ、学祭団体で開発中の自社決済「PaySys」経由でクレジットカード・PayPayの両方を提供する方針に変更**しました。ただし、PaySys自体の実装(実際にお金のやり取りをする部分)はまだ完成しておらず、**現時点では「決済が成功したことにするモック(見せかけの動作)」のみが用意されている状態**です。実際のお金のやり取りは、後任のフロントエンド担当者が別途実装する予定です。

また、これに合わせて「**注文が二重に作られてしまう不具合**」「**アプリを再読み込みすると注文の行方がわからなくなる不具合**」の元となっていた設計も直しました。

### 詳細な解説

- **経緯**: 開発初期にSquareでのクレジットカード決済を実装していましたが、学祭団体側で自社決済システム「PaySys」を用意する方針が確定したため、Square関連のコード一式を`src/legacy/square/`というフォルダへ移動し、**削除はせず保管**しました(将来Squareに戻す可能性や、実装の参考にする可能性を考慮)。各ファイルの冒頭には「⚠️ 未使用」というコメントを入れてあります。
- **注文作成タイミングの変更(根本的なバグ修正)**: 以前は「決済画面を開いた瞬間」にバックエンドへ注文データを送信していました。このため、決済画面を開いてからカートに戻ってもう一度決済画面を開くと注文が2件作られてしまったり、決済の途中でページを再読み込みすると、作成済みの注文がアプリ側から見えなくなり「宙に浮いた注文」になってしまう問題がありました。これを、「**実際に課金する直前**」に注文を作成するタイミングへ変更することで、根本的に解消しました(`src/features/payment/paymentSession.ts`)。
- **モックスイッチ(`USE_MOCK_PAYMENT`)による切り替え**:
  - オン(現在の既定値) → バックエンドへは一切接続せず、決め打ちの注文番号(例: `PAYSYS-CARD-MOCK-ORDER`)で「決済成功」画面まで進めます。これは開発・動作確認用の迂回策で、**実際にお金のやり取りは一切発生しません**。
  - オフ → 「クレジットカード決済(PaySys)は未実装です。後任担当者が実装予定です。」という、実装されていないことが分かる明確なエラーを表示します(実装されていないのに、あたかも動いているように見せかけることはしません)。
  - カード用・PayPay用でほぼ同じ内容のコードが2箇所にあったため、のちの品質改善(セクション6)で1箇所にまとめています。
- **APIの通信内容の不整合を修正**: バックエンド側の実際のAPIパス(`/api/orders/set`等)とフロントが呼んでいたパスが微妙にズレていた問題、送信するデータの形(必須項目の不足等)がバックエンドの想定と合っていなかった問題を修正しました。
- 関連ファイル: `src/hooks/useCardPaymentFlow.ts`, `src/hooks/usePayPayPaymentFlow.ts`, `src/features/payment/paymentSession.ts`, `src/services/apiService.ts`, `src/constants/config.ts`, `src/legacy/square/`配下一式

## 2. カートの中身の管理方法を変更(商品とドリンクの紐付け方式の刷新)

### ひとことで言うと

「角煮ドリンクセット」のようなセット商品を選ぶと、どの飲み物が何個入っているかを内部的に管理する必要があります。以前の管理方法は、バックエンド側の商品登録の仕組みと相性が悪く、**特定の状況で注文が失敗したり、決済処理自体がエラーで止まってしまう可能性がある**設計でした。この管理方法を、バックエンド側でも無理なく扱える形に作り直しました。

### 詳細な解説

- **旧設計の問題**: 以前は「セット商品のID + ドリンクの種類」を組み合わせて、まるで1つの実在する商品であるかのような架空のID(例: 「コーラ入りセット」= ID 41)を作り出し、それをそのままバックエンドへ送信していました。しかし、バックエンドの商品登録の仕組み上、このような架空のIDを持つ商品をあらかじめ登録しておく手段がなく、実在しないIDを送ると注文作成が失敗したり、決済計算の処理中にエラー(NullPointerException)が起きる可能性がありました。
- **新設計**: 商品ID(例:「角煮ドリンクセット」)と、ドリンクの種類ID(例:「コーラ」)を**組み合わせず、別々の情報として**バックエンドへ送るように変更しました。「セットを2個」「コーラを1個・オレンジを1個選んだ」という生のデータだけを送り、「どのセットにどのドリンクが入っているか」を決める計算はバックエンド側で行う方針にしています(この計算ロジック自体は`src/features/order/cartOrganizer.ts`に参考実装として残してあり、バックエンド側の実装の参考にできます)。
- **画面表示の作り直し**: カート確認画面や番号札画面で使う表示部分(`src/components/Order.tsx`)も、この新しいデータの持ち方に合わせて作り直しました。「商品(価格あり)」と「選んだドリンク(価格なし、種類ごとの合計数のみ)」を、紐付けずに2つの独立したリストとして表示するようにしています。
- 関連ファイル: `src/constants/items.ts`, `src/hooks/useAppFlow.ts`, `src/utils/orderUtils.ts`, `src/components/Order.tsx`, `src/features/order/cartOrganizer.ts`

## 3. メニュー(商品一覧)をバックエンドから取得するように変更

### ひとことで言うと

以前は商品の値段・商品名・画像が、アプリのコードの中に直接書き込まれていました(=バックエンド側で値段を変えても、アプリ側のコードを直さない限り反映されない状態)。これを、**バックエンドから毎回最新の情報を取得して表示する**ように変更しました。あわせて、通信がうまくいかなかった場合に、古い情報でごまかさず「取得できませんでした」とはっきり表示する仕組みも入れました。

### 詳細な解説

- `src/hooks/useMenuItems.ts`が、メニュー画面に入るたびにバックエンドの`GET /api/items/get/allItems`から価格・商品名・画像パス・在庫状況(売り切れかどうか)を取得するようにしました。
- **モックスイッチ(`USE_MOCK_MENU`)**: オンの場合は開発・動作確認用に、バックエンドへ一切接続せず決め打ちの値だけでメニュー画面を表示できます(バックエンドを起動していなくても画面の見た目を確認できて便利です)。オフの場合、取得に失敗しても**古いハードコード値へ黙って切り替えることはせず**、「メニューを取得できませんでした」という表示と「再読み込み」ボタンを出します。
- **売り切れの連動ルール**: 「角煮 単品」が売り切れなら、それを含む「角煮ドリンクセット」も自動的に売り切れ扱いにする、といった連動ロジックをフロント側に用意しました(`src/features/soldout/soldoutPolicy.ts`)。バックエンドは商品単位の在庫状況しか返さない前提のため、この連動計算はフロント側で行っています。
- 関連ファイル: `src/hooks/useMenuItems.ts`, `src/features/soldout/soldoutPolicy.ts`, `src/constants/mocks/menuMock.ts`, `src/pages/MenuPage.tsx`

## 4. 開発の土台を刷新(TypeScript化 + ビルドツールの入れ替え)

### ひとことで言うと

アプリの中身(画面の見た目や動作)は変えずに、**コードを書くための土台(裏側の仕組み)を新しくしました**。具体的には、(1) コードに「型」という間違い防止の仕組みを全面的に導入(TypeScript化)、(2) アプリを組み立てる仕組み(ビルドツール)を、今まで使っていた古い方式(Create React App)から、より高速で現在主流の「Vite」という仕組みに入れ替えました。**この変更によってユーザー(お客様)から見た画面や操作性は一切変わりません。** 開発のしやすさ・引き継ぎのしやすさのための裏方の変更です。

### 詳細な解説

- **TypeScript化**: これまでのコードは主にJavaScript(`.js`/`.jsx`)で書かれていましたが、「この変数には数字しか入らない」「この関数はこの形のデータを受け取る」といった約束事をコード自体に書き込めるTypeScript(`.ts`/`.tsx`)へ、ほぼ全ファイルを変換しました。約束事に反するコードを書くとその場でエラーとして検出できるため、バグを未然に防ぎやすくなります。
- **ビルドツールの入れ替え(Create React App → Vite)**: これまで使っていた「Create React App(react-scripts)」という仕組みは、開発コミュニティ内で更新が止まりつつあり、TypeScriptの新しいバージョンとの相性問題も出始めていたため、より現在主流で高速な「Vite」という仕組みに入れ替えました。開発中の画面更新速度が大きく向上しています。
- **テストの仕組みは変えていません**: テスト(自動で正しく動くか確認する仕組み)は「Jest」という仕組みのまま維持しています。Vite標準の「Vitest」への切り替えも検討しましたが、既存のテストの書き方(特定のモジュールを毎回読み直す特殊な書き方)を書き換えるとテストの意味が変わってしまうリスクがあったため、あえて変更しませんでした。
- 環境変数(`.env`ファイルで設定する値)の名前も、Viteの流儀に合わせて`REACT_APP_`から`VITE_`へ変更しています。
- 関連ファイル: 実質ほぼ全ての`src/`配下のファイル(拡張子変更)、新設: `vite.config.ts`, `tsconfig.json`, `babel.config.cjs`, `jest.config.cjs`, `index.html`(ルート)。詳しい技術的経緯は[docs/frontend-handover.md](./frontend-handover.md)の「開発環境・ビルドツール」の章参照。

## 6. コードの品質を底上げ

ここまでの変更が完了した後、改めてコード全体を見直し、**「読みにくい・直しにくい・気づきにくい」箇所がないか**を点検し、見つかった問題を修正しました。

### 6-1. 同じ内容が複数箇所に散らばっていた問題を解消

**ひとことで言うと**: 「最終受付時刻は17時10分」というルールが、コードの中に**2箇所、しかも少し違う書き方で**存在していました。これでは、将来「受付時間を17時30分に変更したい」となったときに、片方だけ直して、もう片方の直し忘れに気づかない、という事故が起きかねません。同様の「同じことが複数箇所に書かれている」問題をいくつか見つけて、1箇所にまとめました。

**詳細な解説**:
- 最終受付時刻(17:10)の判定が、`src/constants/stepRules.ts`(ボタンを押せなくする判定)と`src/features/reservation/reservationSchedule.ts`(選べる時刻の候補を作る処理)の2箇所に、微妙に違う条件式(ちょうど17:10を含めるか含めないか)で存在していました。しかも`stepRules.ts`側の実装は、実際には一度も使われていない「死んだコード」であることも判明しました。共有の関数`isPastLastOrderTime()`を新設し、両方がこの1つの関数を参照するように統一しました。あわせて、「ちょうど17:10は受付終了とする」というルールの意図をユーザー(伊知川)に確認の上、統一しています。
- `src/features/soldout/soldoutPolicy.ts`(売り切れ連動ロジック)が、商品IDを`40`や`91`といった生の数字で直接書いており、他のファイルで使われている名前付きの定数(`PRODUCT_CATEGORIES.PORK_DRINK_SET`等)を使っていませんでした。ID体系を統一しました。
- `src/constants/items.ts`自身の中で、同じ商品ID一覧が2つの異なる書き方で二重に定義されていました。片方から自動的に導き出す形に修正しました。
- カード決済・PayPay決済の2つのフック(`useCardPaymentFlow.ts`/`usePayPayPaymentFlow.ts`)が、ほぼ同じ内容のコードを別々に持っていました。共通部分を`src/hooks/useMockPaymentFlow.ts`に1つにまとめ、決済手段ごとの違い(モック注文番号・エラー文言)だけを個別に指定する形にしました。

### 6-2. テストが薄かった箇所への追加

**ひとことで言うと**: 「自動テストが通っている」ことと、「本当に大事な部分がテストされている」ことは別問題です。調べたところ、**画面遷移やカート操作の中核部分、決済処理の中核部分に、テストが1つもない**ことが分かりました。ここにテストを追加しました。また、「apiService.test.jsというテストファイルがあるから安心」と思いきや、実際には**すでに使っていない古いSquare関連の機能しかテストしていなかった**ことも判明し、整理しました。

**詳細な解説**:
- 画面遷移・カート操作の中核ロジック(`src/hooks/useAppFlow.ts`)、決済フック(`src/hooks/useMockPaymentFlow.ts`)、フッターボタンの表示/無効化ルール(`src/constants/stepRules.ts`)にテストを新規追加しました。
- バックエンドへ実際に送信する`createOrder`/`fetchAllItems`/`fetchOrder`のテストを新規追加し、既に使われていない`getSquareConfig`(Square専用)のテストは`src/legacy/square/__tests__/`へ移動しました。
- テスト数は33件から67件に増えています(`npx jest`で実行、19 suites / 67 tests 全通過)。

### 6-3. 自動チェックの仕組みを導入

**ひとことで言うと**: コードの書き方の間違い(未使用の変数を残したままにする等)を自動で指摘してくれる「ESLint」という仕組みが、実は**設定ファイルだけあって全く機能していない**状態でした。これを実際に動く状態にしました。また、GitHubへコードを送る(push・プルリクエスト)たびに、自動でテスト・ビルド・チェックを走らせる仕組み(CI/CD)も新しく導入しました。

**詳細な解説**:
- `eslint`本体がインストールされておらず、`.eslintrc.json`が存在するだけの「動かない飾り」状態だったのを、実際に機能する状態にしました(`npm run lint`で実行可能)。
- 使っている自動チェックのライブラリ(eslint-plugin-react-hooks)の最新の初期設定は、非常に厳格なルール(まだ本プロジェクトでは使っていない「React Compiler」という先端機能向けの純粋性チェック)を大量に含んでおり、そのままだと動作確認済みの正常なコードまでエラー扱いにしてしまうことが分かったため、実際にバグを見つけられる基本的な2つのルールだけを有効にする調整をしました。
- 日本語の全角スペース(「1個　¥500」のような表記)を「不正な空白」として誤検知する問題も、日本語UIであることを踏まえて設定で調整しました。
- `.github/workflows/ci.yml`を新設し、GitHubへコードを送るたびに「チェック→テスト→ビルド」が自動で走るようにしました。

### 6-4. その他の細かい改善

- レンダー中に予期しないエラーが起きても、白い画面になって何も表示されなくなるのを防ぐ「エラーバウンダリ」という仕組みを追加しました(`src/components/ErrorBoundary.tsx`)。万一のエラー時も「エラーが発生しました・再読み込み」という案内が表示されるようになります。
- `package.json`のプロジェクト名が、開発初期のひな形のまま`"react"`になっていたのを、`"school-festival-2"`に修正しました。
- 使われていない設定項目(`TIMEOUTS`/`RETRY_CONFIG`)に「未使用」の注記を追加し、他の未使用項目との表記を揃えました。

## 7. 今後、注意していただきたいこと

- **決済(PaySys)は現時点で「見せかけ」の状態です。** 実際にお金のやり取りをする部分は未実装で、後任のフロントエンド担当者が実装する必要があります(セクション1参照)。
- **本番公開前に、必ず3つの「モックスイッチ」(`VITE_USE_MOCK_PAYMENT`/`VITE_USE_MOCK_MENU`/`VITE_USE_TEST_TIME`)を全てオフにしてください。** オンのままだと、決済・メニュー・時刻のいずれかが本物のバックエンドに接続されず、見せかけの動作のままになってしまいます。
- **予約の受付時間の制限が、現状フロント(このアプリ)側でしか行われていません。** バックエンドのAPIを直接叩けば、受付時間外の予約も作成できてしまう状態です。バックエンド側への対応依頼は済んでいますが(`docs/backend-requirements.md` 9番)、未対応です。
- その他の技術的な懸念事項・未対応事項は[docs/frontend-handover.md](./frontend-handover.md)の「既知の懸念事項」の章に一覧でまとめてあります。
